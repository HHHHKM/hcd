## 1 工作规则

1. **先写失败的测试，再修。** 每个缺陷修复都要附一条「修复前失败、修复后通过」的测试，测试名以任务编号开头，例如 `it('A1 trusts X-Forwarded-For only from the configured proxy', …)`。
2. **不改现有测试的断言来让测试通过。** 只有在组件拆分导致导入路径或渲染包装变化时，才可以改测试的非断言部分；每处改动在 `FIX_REPORT.md` 里说明。
3. **不连接任何真实外部服务。** 不发真实邮件、不发飞书、不部署生产环境；SMTP、飞书、OAuth 客户端一律用本地 fixture。只使用临时目录里的测试数据库。
4. **如实报告。** jsdom 或 API 测试不能算作浏览器验收；没执行的步骤写「未执行」并说明原因，不写「通过」。
5. **只用规格允许的依赖。** 依赖白名单见 BUILD_SPEC §3。本轮会用到的都在白名单内：`pino`、`react-router`、`react-i18next`、`eslint`、`typescript-eslint`、`eslint-plugin-react-hooks`、`prettier`。
6. **数据库变更必须可迁移。** 已有数据库升级后数据不丢；迁移写进 `db.ts` 的迁移逻辑，并有测试覆盖「旧库升级」。
7. **每个阶段结束都跑一次 `pnpm verify`**，把真实的测试数、文件数、失败项写进 `FIX_REPORT.md`，再进入下一阶段。
8. **以下已有设计不要破坏**（审查中确认是好的）：
   - 写操作的 `X-HCD-Request` 头和 Origin 校验
   - scrypt 密码；会话、令牌、邀请、分享链接、验证码只存哈希
   - 渲染域隔离、5 分钟签名地址、raw 块 CSP 和 sandbox、SVG 白名单重写
   - ZIP 导入的目录校验（路径穿越、压缩炸弹、CRC）
   - OAuth 的 PKCE S256、授权码重用撤销、refresh 轮换与重放检测、客户端元数据的公网 IP 限制
   - 发布在 IMMEDIATE 事务内进行并重新校验身份；提交幂等键
   - 合并引擎的保守策略：有未解决冲突的提交整体不进入候选版本

## 4 阶段 A：部署前必须修

### A1 反向代理后的真实客户端 IP

- **问题**：`packages/server/src/app.ts:305` 创建 Fastify 时没有 `trustProxy`。部署方案（`deploy/docker-compose.yml`、`deploy/Caddyfile`）由 Caddy 反代到 `app:3000`，所以 `request.ip` 永远是 Caddy 容器地址，所有按 IP 的限流变成全站共用：
  - 登录：`app.ts:537`（全站 15 分钟累计 20 次失败后所有人都被拒绝）
  - 访客接口：`app.ts:311`；访客验证码：`guests.ts:44`
  - 忘记密码：`app.ts:596`；OAuth：`oauth.ts:40`；CLI 授权：`cli-auth.ts:45`
- **要求**：
  1. 新增环境变量 `TRUST_PROXY`，取值为逗号分隔的 IP 或 CIDR，传给 Fastify 的 `trustProxy`；未设置时为 `false`（直接暴露端口时不信任任何转发头）。`createApp` 的选项里也加 `trustProxy`，便于测试。
  2. `deploy/docker-compose.yml` 给默认网络固定子网（例如 `172.28.0.0/24`），并设置 `TRUST_PROXY` 为该子网；`deploy/.env.example` 和 `deploy/README.md` 同步说明。
  3. 不要用 `trustProxy: true`。
  4. 检查所有使用 `request.ip` 的地方，确认取到的是真实客户端 IP。
- **验收测试**（用 `app.inject` 的 `remoteAddress`）：
  - 来自受信代理、`X-Forwarded-For` 不同的两个客户端，限流互不影响
  - 来自不受信地址时伪造的 `X-Forwarded-For` 被忽略
  - 未设置 `TRUST_PROXY` 时行为与现在一致

### A2 CLI 令牌格式与 MCP 一致

- **问题**：`cli-auth.ts:42` 的 `credential()` 生成 `hcd_pat_` + 43 位 base64url（HMAC 结果）；`mcp.ts:94` 的 `bearer()` 只接受 `hcd_pat_` + 32 位 base32。结果是 `mdoc login` → `mdoc mcp` 必然 401（「Cannot connect to HCD MCP」）。REST 接口不校验格式，所以 pull、submit 正常，现有测试没发现：`mcp-relay.test.ts` 只用了网页 `/me/tokens` 创建的令牌。
- **要求**：
  1. 修改 `credential()`：取 HMAC 结果的前 20 字节，用与 `app.ts` 中 `base32()` 相同的字母表编码，得到 32 位。保持确定性派生，`available()` 中的哈希比对随之一致。
  2. 把令牌格式定义成一个共享常量或正则（例如放在 `packages/core/src/`），由网页 PAT 生成、CLI 授权、MCP 校验、CLI 本地校验（`packages/cli/src/index.ts:250`、`device-login.ts:54`）共同使用，避免再次不一致。
- **验收测试**：
  - 完整设备授权流程拿到的令牌，直接调用 `POST /mcp` 的 `initialize` 返回 200
  - `mcp-relay` 用设备授权令牌端到端调用一次工具成功
  - 令牌格式符合 §20.5

## 5 阶段 B：后端缺陷与规格补齐

### B1 版本历史显示作者名字

- **问题**：`app.ts:1591`（`/docs/:id/versions`）和 `app.ts:1601`（`/docs/:id/versions/:version`）只返回 `createdBy` 用户编号；`packages/web/src/VersionComparison.tsx:17` 找不到 `authorName` 时直接显示编号。截图 `outputs/browser-version-compare.png` 中显示为「创建者：u_owner000000」。
- **要求**：两个接口关联 `users` 表返回 `authorName`；前端拿不到名字时显示「未知用户 / Unknown user」，任何情况下不显示内部编号。
- **验收**：接口测试断言返回名字；组件测试断言渲染名字、不出现 `u_` 编号。

### B2 固定版本链接的评论过滤（决策 D-1）

- **问题**：`app.ts:1257` 的 `GET /s/:token/comments` 不按版本过滤，固定 v1 的链接能看到成员针对 v2 写的评论正文；`app.ts:1228` 的 `GET /s/:token/doc` 还返回了 `currentVersion`。
- **注意**：不能用评论锚点里的 `version` 判断创建版本——每次发布都会把它改成新版本（`app.ts:1568`）。
- **要求**：
  1. `comments` 表新增 `created_version INTEGER`，写入「作者创建时看到的版本」：成员为当时的正式版本；访客为其链接可见的版本（固定链接即 `version_pin`）。根评论和回复都要写。
  2. 迁移已有数据：访客评论若其链接有 `version_pin`，取 `version_pin`；其余取「创建时间之前最新发布的版本号」，找不到时取 1。
  3. 固定链接（`version_pin` 不为空）的 `GET /s/:token/comments`：
     - 根评论：只返回 `created_version ≤ version_pin` 的
     - 回复：只返回 `created_version ≤ version_pin` 的；但**根评论由访客发起的主题，返回其全部回复**
  4. 固定链接的 `POST /s/:token/comments` 回复时，父评论必须对该链接可见，否则返回 404。
  5. 固定链接的 `GET /s/:token/doc` 不返回 `currentVersion`，只返回 `version`。
  6. 非固定链接的行为保持不变。
  7. 成员端：在「由外部访客发起的主题」的回复框上方提示「此主题的回复对外部访客可见 / Replies in this thread are visible to the external guest」。
- **验收测试**：v2 上的成员评论对 v1 固定链接不可见；v1 时期的评论可见；访客在固定链接上的评论和成员在该主题下的回复对该链接可见；成员在成员主题下 v2 之后的回复不可见；回复不可见主题返回 404；固定链接响应中没有 `currentVersion`；旧库迁移后访客评论仍对其链接可见。

### B3 忘记密码按规格限频

- **问题**：`app.ts:596` 同一邮箱每分钟 1 次（约每小时 60 封）；规格 §14.2 为每邮箱每小时 3 次。计数在内存里，重启后清零。
- **要求**：改为每邮箱每小时 3 次，计数存数据库（邮箱存哈希）；无论是否命中限制都返回 204，不暴露邮箱是否存在。IP 维度的限制保留（依赖 A1 取到真实 IP）。
- **验收**：同一邮箱第 4 次请求不再写入发件箱；窗口过后恢复；用同一数据库重新 `createApp` 后计数仍有效。

### B4 历史对比不阻塞进程

- **问题**：`app.ts:1603` 的 `/compare` 同步计算，5000 段文档约 1.4 秒（见 `outputs/history-diff-benchmark.json`），期间整个进程无法响应其他请求；viewer 权限就能调用，每人每分钟最多 300 次。
- **要求**（实现方式可自选，必须满足验收标准）：
  1. 已发布版本不可变，按（文档、from、to）缓存对比结果，缓存要有容量上限。
  2. 首次计算不能阻塞主线程，例如放进 `worker_threads`。如果用 worker，生产构建（`deploy/Dockerfile` 打包成 `server-build/main.mjs`）也要能加载 worker 入口。
  3. `/compare` 单独限流，额度参照规格 §20.4 中导入、上传、导出的额度（每人每分钟 10 次）。
  4. 检查预览生成里的 `reviewPresentation`（`change-presentation.ts`）是否有同样的同步大计算，有则同样处理。
- **验收**：5000 段文档对比进行中，并发的 `GET /healthz` 在 100ms 内返回；同一对比第二次请求在 50ms 内返回；更新 `outputs/history-diff-benchmark.json`。

### B5 请求日志（规格 §20.6）

- **问题**：`app.ts:305` 为 `logger: false`，pino 已在依赖里但没用，上线后出问题无日志可查；MCP 里的 `app.log.error` 实际不输出。
- **要求**：
  1. 关闭 Fastify 默认请求日志，在 `onResponse` 统一写一行 JSON：方法、**路由模板**、状态码、耗时、用户编号（访客写访客编号）、请求编号。
  2. 必须记录路由模板（例如 `/api/v1/s/:token/doc`），**不能记录原始路径**——分享链接、邀请、重置、CLI 授权码都在路径里。查询字符串一律不记。
  3. 不记录请求体、文档内容、评论正文、密码、令牌、Cookie、验证码。
  4. `LOG_LEVEL` 环境变量控制级别；测试中默认静默。
- **验收测试**：访问分享链接、接受邀请、登录各一次，日志里不出现令牌、密码、邀请码；日志包含路由模板、状态码和耗时。

### B6 退出全部设备（规格 §14.2）

- **要求**：新增 `POST /api/v1/auth/logout-all`：需要登录 Cookie（拒绝令牌），校验 `X-HCD-Request` 和 Origin，删除该用户全部会话，清除当前 Cookie，返回 204。在个人设置页（`/settings`）加按钮，页内二次确认。
- **验收**：两个会话登录同一账号，任一会话调用后两个会话都返回 401；令牌不受影响。

### B7 登录后修改密码（规格 §14.2）

- **要求**：`PATCH /me` 支持 `currentPassword` + `newPassword`（10–1024 字符）。旧密码错误计入该邮箱的登录失败次数，沿用登录的限流；成功后更新密码、删除该用户除当前会话外的所有会话、作废未使用的重置链接。个人设置页加表单，有标签和错误提示。
- **验收**：旧密码错误返回错误且不改密码；连续错误触发限流；成功后其他会话 401、当前会话可用、新密码可登录。

### B8 令牌最近使用时间和 IP（规格 §20.5）

- **要求**：`api_tokens` 增加 `last_used_at`、`last_used_ip`；令牌通过认证时更新，同一令牌每分钟最多更新一次。`GET /me/tokens` 返回这两项，个人设置的令牌页显示。
- **验收**：使用令牌后能看到时间和 IP；一分钟内多次使用只写一次库。

### B9 评论「解决」权限按规格（规格 §12.1）

- **问题**：`app.ts:1809`、`app.ts:1819` 只允许主题发起人或负责人解决、重新打开；规格是「解决自己参与的主题」。
- **要求**：负责人可以解决任意主题；commenter 及以上角色，只要在该主题里发过未删除的评论或回复，也可以解决和重新打开。令牌需要 `comment` 范围。
- **验收**：回复过的评论者可以解决；未参与的编辑者返回 403；viewer 返回 403。

### B10 MCP 内部调用不重复计入限流

- **问题**：`mcp.ts:252`、`mcp.ts:267` 每次 MCP 请求内部调两次 `/me`；`list_documents`（`mcp.ts:146`）对每篇文档再调一次。全部计入用户每分钟 300 次的额度，文档一多，一次调用就会被限流。
- **要求**：
  1. `list_documents` 直接使用 `/docs` 的结果（它已经按令牌范围和 AI 开关过滤），去掉逐篇调用。
  2. MCP 每个 HTTP 请求、每次工具调用各只计一次用户额度；内部 `inject` 请求不再计数。标记内部请求时，用进程启动时随机生成的密钥并做常量时间比较，**不能用外部请求可以伪造的固定头**。
- **验收**：有 50 篇 AI 已开启文档时，`list_documents` 一次调用不触发限流；外部请求伪造内部标记无效。

### B11 生产环境禁止写入演示数据

- **问题**：`main.ts:21` 在生产环境设置 `HCD_SEED_DEMO=1` 时仍会写入演示账号，管理员密码是公开的。
- **要求**：`NODE_ENV=production` 且 `HCD_SEED_DEMO=1` 时启动失败，并给出明确错误信息。
- **验收**：启动检查测试。

## 6 阶段 C：前端（修复与工程化，不做整体视觉改版）

本阶段目标：功能问题修好，代码结构、路由、双语、样式令牌达到规格要求。整体视觉风格保持现状，之后由 Claude 做改版。

### C1 拆分 App.tsx

- **问题**：`packages/web/src/App.tsx` 85KB，一个组件里有 60 个 `useState`，最长一行 7,544 个字符，超过 300 字符的行有 42 行。
- **要求**：
  1. 按功能拆分，例如 `app/`（外壳、路由、全局上下文）、`features/document/`、`features/comments/`、`features/review/`、`features/history/`、`features/settings/`、`features/admin/`、`shared/`（api、hooks、通用组件）。
  2. 单个文件不超过 400 行；加 prettier（`printWidth: 120`）并格式化 `packages/web`。
  3. 全局状态（当前用户、语言、当前文档）用 context；数据请求用带 `AbortController` 的 hooks，切换文档时取消旧请求，避免旧响应覆盖新页面（TEST_PLAN P2「切文档旧请求返回」）。
